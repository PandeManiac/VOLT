
# VOLT Vulkan Cube: Device-Local Vertex Pulling

A continuously rotating, depth-tested Vulkan cube demonstrating
VOLT's graphics infrastructure, custom vertex pulling, and staged
GPU buffer uploads.

## Features

- Continuous Vulkan rendering until the window closes
- Perspective projection and rotation around two axes
- Six individually colored cube faces
- Hardware depth testing
- SDL3 event polling
- Explicit GPU synchronization and resource ownership
- Descriptor-backed storage buffers
- Shader-driven vertex pulling
- Compact, application-defined geometry descriptors
- Host-visible staging buffers
- GPU-side copies into device-local memory

## Vertex Pulling

The cube uses six 32-bit face descriptors stored in a Vulkan
storage buffer.

Each descriptor encodes:

| Bits | Purpose |
|---|---|
| 0-1 | Face axis |
| 2 | Positive or negative direction |
| 3-5 | Face color |

Each face is rendered as two triangles, generated by the vertex
shader from its packed descriptor.

The renderer issues a draw with six vertices and six instances.
The shader uses `gl_InstanceIndex` to select the face descriptor
and `gl_VertexIndex` to reconstruct the face geometry.

There are no conventional vertex attributes or vertex-buffer
bindings.

The packing format is specific to this sample. It is not a
required VOLT vertex format.

## GPU Buffer Infrastructure

The sample uses `VulkanBuffer` and `VulkanBufferTransfer` from
`Volt.Graphics.Vulkan.Memory`.

`VulkanBuffer` provides:

- Application-defined buffer usage flags
- Vulkan memory-type selection
- Required and preferred memory properties
- Typed uploads to host-visible memory
- Non-coherent memory flushing
- Explicit native resource cleanup

`VulkanBufferTransfer` adds:

- Temporary host-visible staging buffers
- Synchronous buffer-to-buffer copies
- Device-local destination allocations
- Explicit transfer-to-consumer memory barriers
- Fence-based completion tracking
- Copy-region validation

### Upload process

1. Create a host-visible staging buffer.
2. Copy application data into the staging buffer.
3. Create a device-local destination buffer.
4. Record a Vulkan buffer copy.
5. Record a memory barrier for later buffer consumers.
6. Submit the copy to the graphics queue.
7. Wait for completion.
8. Destroy the temporary staging buffer.
9. Use the persistent destination buffer for rendering.

The cube's geometry is uploaded once during initialization.

## Requirements

- .NET 10 SDK
- Vulkan-capable GPU and driver
- SDL3 runtime dependencies
- glslangValidator
- Optional Vulkan validation layers

On Arch Linux:

```bash
sudo pacman -S --needed glslang vulkan-validation-layers
```

## Build

From the repository root:

```bash
dotnet build Volt.slnx -c Release
dotnet test Volt.slnx -c Release --no-build
```

## Run

Wayland:

```bash
SDL_VIDEODRIVER=wayland dotnet run \
  --project samples/Volt.VulkanCubeDemo \
  -c Release -- --validation
```

X11:

```bash
SDL_VIDEODRIVER=x11 dotnet run \
  --project samples/Volt.VulkanCubeDemo \
  -c Release -- --validation
```

Close the window to exit.

## Limitations

This is a focused graphics sample, not the final VOLT renderer.

- Only one graphics submission is in flight.
- The depth attachment is shared between framebuffers.
- The window is intentionally non-resizable.
- Swapchain recreation is not yet supported.
- Staging transfers are synchronous.
- Each VulkanBuffer owns a dedicated memory allocation.
- No persistent upload ring or batched transfer scheduling exists.
- No dedicated transfer queue is used.
- No buffer device address support is required.
- There is no engine-defined mesh or material system.
- The sample does not yet render ECS-managed scene objects.

For frequently changing geometry, a future upload system should
batch transfers, reuse staging allocations, and manage the
lifetime of in-flight GPU resources asynchronously.

## Resource Ownership

Vulkan buffers and allocations must outlive GPU commands that
reference them.

The staged upload helper waits for completion before destroying
its temporary transfer resources.

The cube demo waits for the device to become idle before
destroying its persistent rendering resources.

Application code must still synchronize CPU uploads and GPU
accesses when updating buffers that may already be in use.

The general buffer abstraction does not automatically track
pending GPU accesses or insert barriers for unrelated operations.
